# 解決キャッシュの設計 (提案)

提出 (`SubmitEvent`) の残りの処理時間を削るための設計。実装前の提案であり、
現在の仕様は [service.md](service.md)「型検査」と
[incremental-type-check.md](incremental-type-check.md) にある。

## 背景と測定

高速化は 2 段済んでいる:

- ホストのコミット/定義キャッシュの D1 永続化 (#853):
  冷たい提出 約 2.7 秒 → 約 1.23 秒
- 増分型検査 (#855): 型が変わっていないパーツの再検査をやめた。
  `definy` (850 パーツ) への 1 パーツ追加 約 1.26〜1.38 秒 → 約 0.88〜1.06 秒

残りの内訳を 2026-11-04 に測った (ローカル、温かい状態):

- 中身が同じコピーコミット (検査対象が実質ゼロ) でも `definy` は約 1.2 秒。
  そのうち DB (SQL) は 3 回・約 7ms で、残りはほぼ全て definy 側の処理
- 自明なパーツ (型は number、式は数値リテラル) を 850 個持つプロジェクトでも
  コピーコミットが約 1.0 秒。つまり支配的なのは中身の複雑さではなく
  **パーツ数に比例する処理** (1 パーツあたり約 1.2ms) である

毎回の提出で、全プロジェクトの最新コミットと対象コミットの全パーツについて
「中身 (CAS) → 定義 → 解決済みの中身 (`core.part-content`) → 型検査エントリ」を
組み立て直している。コミット単位の読み取り (#853 の `read_cached_commits`) と
定義そのもの (`read_cached_definitions`) はキャッシュされるが、
**解決とエントリ組み立ては毎回 definy の中でやり直している**。ここが残りの大半。

当初の段階 2 案は「検査結果を閉包署名キーでキャッシュする」だったが、
コピーコミット (検査結果の再利用が効かない場面) が遅いことから、
先にこちらをやるべきだと分かった。検査結果キャッシュは必要なら後続に残す。

## 何をキャッシュするか

キー = パーツの中身の **content hash**、値 = その中身から得られる

- 解決済みの中身 (`core.part-content`)
- 型検査エントリ (`definy.type-check-entry`)

の組。エントリは解決済みの中身の純粋な関数 (`definy.content-type-check-entry`) なので
一緒に保存できる。content hash は中身そのものの SHA-256 で、中身は不変だから
キーと値の対応は永遠に正しい (#853 のキャッシュと同じ性質)。

### 健全性: 即時解決できるパーツだけを対象にする

中身の解決には 2 経路ある (`definy.resolve-commit-contents`):

- **即時解決** (`definy.immediate-part-content`): 定義がリテラルな
  `define-part` / `define-type` 呼び出しで、そのまま中身になる。
  結果はそのパーツ自身の定義だけの純粋な関数
- **保留→評価**: 定義が他のパーツを参照する計算を含む場合、参照先の内容に
  依存するので、自分の content hash だけでは結果が決まらない

キャッシュに書くのは即時解決できたパーツだけにする。保留→評価で解決したパーツは
今まで通り毎回評価する (seed コーパスのパーツはほぼ全て即時解決できる。
評価が要る動的生成パーツは少数で、そちらは対象外でも効果の大半は得られる)。

## ホスト側の変更

#853 のキャッシュと同じ形の能力を足す:

- `read_cached_resolutions` (content hash の一覧 → あるものだけ返す)
- `write_cached_resolutions` (content hash と値の組の一覧を保存する)
- D1 に `host_resolution_cache` テーブル (キーは content hash、値は JSON 化した組)。
  メモリ内キャッシュを前に置き、失敗したらメモリだけに倒れる、という
  `worker/commit_store.ts` の既存パターンに合わせる

値は definy の値 (part-content とエントリ) を既存のキャッシュと同じ方法で
JSON 化して保存する。スキーマが変わったら古い値を読めないように、
値には版を含める (読めなければミスとして扱い、再計算して上書きする)。

## definy 側の組み込み

解決の流れ (`definy.read-commit-check-input` と `definy.resolve-latest-commits` が使う
`definy.resolve-commit-contents`) を次のように変える:

1. コミットの全パーツの content hash で `read_cached_resolutions` を引く
   (定義の取得より前にまとめて 1 回)
2. ヒットしたパーツは解決済みとしてそのまま使う。定義の取得もしない
3. ミスしたパーツは従来通り定義を取り、即時解決できたら結果を
   `write_cached_resolutions` に書く。保留→評価に回ったものは書かない
4. 型検査エントリは、ヒットしたパーツについては保存されていたものを使う

環境側 (全プロジェクトの最新コミット) も対象コミットも同じ経路を通るので、
両方に効く。通常の提出では大半のパーツが前回と同じ content hash であり、
ヒット率は高いはずである。

## 段階分け

- **段階 2a (この提案)**: 解決+エントリのキャッシュ (上記)
- **段階 2b (任意・後続)**: 組み立て済みの型環境そのもののキャッシュ。
  型環境は「全プロジェクトの最新コミットの集合 + 対象モジュール」の純粋な関数だが、
  値が大きく、境界を越える変換コストと再構築コストの兼ね合いを 2a の後に測って判断する
- **段階 2c (任意・後続)**: 検査結果のキャッシュ (当初の案)。ブランチをまたいだ
  同じ提出の再利用にだけ効くので優先度は低い

## 検証計画

- 等価性: 既存スイートが無変更で通ること。特に seed の往復と
  `worker/incremental_type_check.test.ts` のシナリオ
- 健全性のシナリオ: 参照先が変わると評価結果が変わる動的生成パーツについて、
  キャッシュが古い結果を返さないこと (保留→評価のパーツはキャッシュされないことの確認)。
  即時解決のパーツは、同じ content hash で必ず同じ結果になることの確認
- 性能: ローカルの提出ベンチで、`definy` へのコピーコミットと 1 パーツ追加が
  どちらも約 0.5 秒以下になることを目標にする。本番では、以前 503 になった
  大きなプロジェクトへの追加コミットが初回から成功するかを確かめる

## 未決事項

- 値の JSON 化の形式 (そのままの definy 値か、part-content とエントリを分けるか) と版の付け方
- `read_cached_resolutions` を引く単位: コミットごと一括か、定義の取得と同じタイミングか
  (実装時に、既存の `definy.read-definitions` の流れに一番素直に乗る方を選ぶ)
- テーブルの肥大化: 中身が増えるほど行は増えるが、content hash キーで不変なので
  掃除は不要という立場を取る (既存のキャッシュテーブルと同じ)
