# 提出パイプラインの索引化の設計 (提案)

提出 (`SubmitEvent`) の残りの処理時間を削るための設計。実装前の提案であり、
現在の仕様は [service.md](service.md)「型検査」と
[incremental-type-check.md](incremental-type-check.md)、
[resolution-cache.md](resolution-cache.md) にある。

## 背景と測定

高速化は 3 段済んでいる:

- ホストのコミット/定義キャッシュの D1 永続化 (#853):
  冷たい提出 約 2.7 秒 → 約 1.23 秒
- 増分型検査 (#855): 型が変わっていないパーツの再検査をやめた
- 解決キャッシュ (#861): 温かい `definy` への提出 約 1.2 秒 → 約 0.95〜1.05 秒

残りの約 1 秒はホスト側ではない (温かいコピーコミットで DB は約 7ms)。
全部 definy 側 (service の wasm) の計算である。2026-11-04 の測定:

| プロジェクト                   | 温かいコピーコミット |
| ------------------------------ | -------------------- |
| 自明なパーツ 100 個            | 約 260ms             |
| 自明なパーツ 200 個            | 約 405ms             |
| 自明なパーツ 400 個            | 約 660ms             |
| 前のパーツを参照する 400 個    | 約 770ms             |
| `definy` (約 870 パーツ、実物) | 約 0.95〜1.05 秒     |

パーツあたり約 1.3ms の傾きがあり、パーツ数に対して増えていく。
支配項は 1 つの大きな処理ではなく、提出パイプラインに散らばる
「全パーツに対する線形探索」と「全パーツを舐めるパスの多さ」である。

## 特定した線形探索

提出の経路を読み、キーで探す処理が全部線形探索になっていることを確認した。
`n` = プロジェクトのパーツ数、`r` = 参照の総数とする。

| 探索するパーツ                                                   | 呼ばれる場所                                                                                                                | 回数                 | 計算量                                             |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------- | -------------------------------------------------- |
| `definy.resolved-content-find`                                   | `definy.commit-check-parts-of` (パーツごと)、`definy.collect-evaluation-parts`                                              | `n` 回               | O(n²)                                              |
| `core.module-entry-lookup`                                       | `core.module-commit-classify`、`core.module-entries-changed-signatures`、`core.module-entries-removed` (いずれもパーツごと) | `n` 回 × 3 パス      | O(n²)                                              |
| `core.visibility-target-find` / `core.visibility-committed-find` | `core.part-reference-violations` (参照ごと)                                                                                 | `r` 回               | O(r × n)                                           |
| `core.part-type-lookup`                                          | `core.type-env-lookup-part` 経由で型検査中のパーツ参照ごと                                                                  | 検査する式の参照ごと | O(r × n)                                           |
| `definy.commit-check-part-find`                                  | `definy.commit-check-requests`、`definy.commit-check-without-expression`                                                    | 検査対象ごと         | O(n²)                                              |
| `definy.resolution-for` (段階 2 のキャッシュ参照)                | 提出まわり数か所                                                                                                            | `n` 回               | O(n²) (ただし要素が小さく実測では支配的でなかった) |

このほか、`core.list-append` で 1 件ずつ積む fold が各所にある。
`list-append` は組み込みだが、リストが不変なら 1 回ごとにコピーが要り、
fold 全体では O(n²) のコピーになる。実行時 (wasm ランタイム) の
表現次第なので、索引化とは別に確認が要る。

## 方針: 並べ替え済み索引 + 二分探索

リストをキー (パーツ ID の文字列) で並べ替えた「索引」を提出ごとに 1 回作り、
探索を二分探索に変える。新しいデータ構造は足さない。
比較には既存の `core.string-less-than` を使い、リストの並べ替え
(マージソート) と二分探索は core に新規の部品として足す。

- 索引は**探索専用**に作る。反復の順序が結果に効く場所 (型環境の構築、
  検査リクエストの生成など) では元のリストをそのまま使い、
  順序を変えない。
- 索引を作るのは、対象リストが提出の中で既に実体化している地点にする
  (解決済みパーツ一覧、分類の前回/今回エントリ一覧、可視性の対象一覧、
  型環境のエントリ一覧)。
- 二分探索の汎用部品を core に置く: キー取り出し関数を渡す形ではなく、
  対象がレコード型ごとに違うので、まずエントリ用
  (`core.module-entry-lookup` の索引版) と ID 引き用
  (definy 側の `resolved-content-find`、`commit-check-part-find` の索引版)
  から始め、形が固まれば寄せる。

段階 2 で解決キャッシュの参照だけを二分探索に変えて効果がなかったのは、
あの参照が提出 1 回あたり最大でもパーツ数回で、要素あたりの処理も
軽かったためである。今回は参照ごと・パーツごとに全リストを舐めている
箇所が対象で、探索回数そのものが桁違いに多い。

## 適用順序

独立にマージできる 3 つに分ける。

1. **3a: definy 側の探索** — `resolved-content-find` と
   `commit-check-part-find` を索引版にする。提出の前段で効き、
   等価性の確認が一番簡単。
2. **3b: 分類の探索** — `module-entry-lookup` を索引版にし、
   classify / changed-signatures / removed の 3 パスで共有する。
   前回エントリ一覧は `core.type-checker` の入口で 1 回だけ並べ替える。
3. **3c: 可視性と型環境の探索** — `part-reference-violations` の 2 つの探索と、
   型検査中の `part-type-lookup` を索引版にする。型環境はモジュールごとに
   組み直される場合があるので、索引を作る地点の見極めが要る。

## 等価性

- パーツ ID はプロジェクト内で一意 (モジュール ID とパーツ名から決まる)
  なので、索引の中でキーは重ならない。二分探索が返す要素は
  線形探索が返す要素と一致する。
- 見つからない場合の結果 (none / エラー) も変えない。
- 既存のテスト (`worker/type_check.test.ts`、
  `worker/incremental_type_check.test.ts`、可視性と提出まわりのテスト) が
  無変更で通ることが条件。加えて、索引版と線形版で結果が一致することを
  直接比べるテストを各段階で足す。

## 期待と限界

- 探索は O(n) → O(log n) になる。温かい `definy` のコピーコミットで
  約 1 秒 → 数百 ms 台を狙うが、全パーツを舐めるパス自体 (エントリの
  組み立て、CBOR の読み書きなど) は残るので、実測で確かめながら進める。
- パスの本数削減 (融合) や表現の見直しはこの設計の外。
  索引化で足りなければ次に検討する。

## 代替案

- core にハッシュマップ (ハッシュトライ) を実装する: 探索は定数時間に
  近づくが、言語側に大きな部品が増え、永続データ構造の実装と検証が重い。
  まずは既存部品で組める索引で十分な効果が見込めるため採らない。
- ホスト側に索引を持たせる: 提出の検査は definy 側の責務であり、
  ホストに検査知識を持ち込むと [service.md](service.md) の分担が崩れる。
  採らない。
