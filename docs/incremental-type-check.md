# 増分型検査の設計 (提案)

`SubmitEvent` の型検査を、プロジェクト単位ではなくパーツ単位で増分にする設計。
実装前の提案であり、現在の仕様は [service.md](service.md)「型検査」にある。

## 背景と測定

ホストのキャッシュを D1 に永続化した (#853) あとの温かい状態でも、
`definy` プロジェクト (236 パーツ) への提出はローカルで約 1.17 秒かかる。内訳:

- 型環境側 (全プロジェクトの main の解決など): 約 130ms (`sample` の提出全体と同程度)
- 対象コミットの定義まわりの処理: 約 0.2〜0.3 秒 (236 個の自明なパーツだけのプロジェクトで提出全体が約 0.3 秒)
- 対象コミットの全パーツの型検査: 約 0.7〜0.9 秒

1 パーツ追加しただけでもプロジェクトの全パーツを検査し直しているのが支配的だった。

## 現在の仕組み

- `definy.check-commit-input` は対象プロジェクトのパーツを置き換えモジュール (`#replaced`) の
  エントリにし、`core.type-checker` に計画 (plan) を作らせる。
  エントリ (`core` の module entry) は `part_id` / `module_id` / `part_type` / `type_declaration` /
  `expression_key` (= content hash) / `has_expression` を持ち、式は型パーツとコンパイラ組み込みのものだけが残る
- 計画は `to_check` (検査するパーツ)、`without_expression`、そして環境を閉じ込めた `check`
  (`core.type-checker-in-env`) からなる。`definy.type-check-requests-errors` が `to_check` の
  パーツを 1 つずつ `check` で検査する。**検査はもともとパーツ単位に分かれている**
- どのパーツを `to_check` に入れるかは `core.module-commit-classify` が決める。
  前回 (main の最新) と比べて `expression_key` が同じパーツは、原則として省かれる。
  ただし `core.module-entries-types-changed` が真だと全パーツが対象に戻る。
  これは「どれか 1 つの型が変わった」だけでなく「パーツの数が変わった (追加・削除)」でも真になる。
  つまり **1 パーツの追加・削除・型変更のたびにプロジェクト全パーツを再検査する** のが現状で、
  測定結果と一致する

## 設計: パーツ単位の影響判定

### 前提

パーツ P の検査結果は、P 自身のエントリと、型環境のうち P が (型の展開を含めて) 参照する
範囲だけで決まる純粋な関数である。他のパーツの「中身 (通常パーツの本体)」は P の検査に使われない。
使われるのは参照先の宣言型 (`part_type`) と、型パーツ・組み込みパーツの式だけであり、
どちらもエントリに残っている。したがって影響範囲はエントリだけから計算できる。

### 署名 (signature)

各エントリ Q について、検査に関わる範囲の Merkle 指紋 `sig(Q)` を定義する:

```
sig(Q) = H(
  Q.part_type のキー,
  Q に式が残っている場合は Q.expression_key、無ければ固定値,
  Q.part_type と (残っている) Q の式に出てくる参照先 R の sig(R) の列 (ソート済み)
)
```

参照先がエントリに無い場合は固定値 (欠落を表す値) を使う。`H` は既存の SHA-256 の仕組み
(content hash と同じ強度で十分) を使う想定で、エントリのキーはすでに content hash なので
材料は揃っている。計算は参照の総数に対して線形で、検査そのものより桁違いに軽い。

### 影響規則

対象プロジェクトの各パーツ P について、次に当てはまれば `to_check` に入れる。当てはまらなければ省く:

1. P が新しい、または P 自身の `part_type` / `expression_key` が前回と違う (現行どおり)
2. P の `part_type` と式に出てくる参照先の閉包の中で、`sig` が前回と違うものがある
   (型が変わった、型パーツの定義が変わった、など)
3. P が参照する先が前回はあったのに今回は無い (削除・改名)。これは閉包の `sig` 比較に
   欠落の固定値を含めることで 2 に含まれる

前回 (previous) の `sig` は、前回のエントリ (main の最新のエントリ列) から同じ定義で計算する。
対象外プロジェクトのパーツは提出の間は変わらないので、環境側の `sig` は前回=今回として扱える。

### 置き換える場所

- `core.module-entries-types-changed` (真偽値) を廃止し、`core.module-commit-classify` には
  「型に関わる変更があった参照先の集合」または各パーツの影響判定そのものを渡す
- 計画の形 (`to_check` / `without_expression` / `check`) と `definy` 側の呼び方は変えない。
  変わるのは「変わっていないパーツが `to_check` に戻る条件」だけ
- `definition_check` (評価して得たパーツの定義の式の検査) と、型検査以外の検査
  (中身の形、参照の可視性など) は現行どおり全パーツに対して行う

## 健全性

- 受け付けられたコミットの列に対する帰納法で考える。各提出で、省かれたパーツは
  「自身も依存先の署名も前回と同じ」であり、前回受け付けられた時点で同じ文脈で検査済みなので、
  今回検査しても結果は同じ (成功) になる。よって省いても受理・拒否とエラーの集合は変わらない
- エラーの報告順: 要求の列の順序は変えず、省かれるのは「前回成功したもの」だけなので、
  報告されるエラーの並びも変わらない
- 削除・改名: 参照先が消えると署名が変わる (欠落の固定値) ので依存先は再検査され、
  見つからない参照はそこで (あるいは可視性の検査で) 拒否される
- 型チェッカー自体が変わった場合 (コンパイラの seed 更新) に過去の受理が再検査されない点は、
  現行の仕組みでも同じ (型が変わらなければ省かれる)。新しいリスクではない
- 前提が崩れる場合に備え、分類の入口で「署名が計算できない・参照が引けない」場合は
  安全側に倒して `to_check` に入れる

## エディタ側への影響

- エディタのコミット時検査 (`checkCommitTypes` → `checkModuleCommitParts`) は、サーバーと同じ
  `core.type-checker` をブラウザでコンパイルして使い、置き換えモジュール (`#replaced`) として
  同じ分類を通る。したがって、この設計はそのままエディタのコミット時検査にも効く
- 編集中の逐次検査 (`useTypeCheck`) は別の仕組みで、パーツごとの検査結果を
  (型環境キー, `expressionKey`) でキャッシュしている。本体のみの変更で再検査しない点は
  既に増分だが、型環境キーはプロジェクト全体で 1 つの文字列 (`workingTypeEnvSignature`) なので、
  型が 1 つ変わると全パーツの再検査になる粗さが残る。ここは今回の署名 (依存閉包の指紋) を
  TS 側のキャッシュキーに使う形で別途細かくできる。段階 1 の対象外とし、フォローアップとして記録する
- パーツ 1 つの検査そのもの (`check`) の速さは両側とも変わらない。変わるのは「どのパーツを
  検査するか」の選択だけである

## 段階 2 (任意・後続)

署名はそのまま永続キャッシュのキーにもなる。ブランチをまたいで同じ状態のパーツが
再提出される場合 (差し戻し、別ブランチへの同じコミットなど) は、`read/write_cached_definitions` と
同じ形の能力 (`read/write_cached_type_checks`、キー = P の閉包署名) で検査結果自体を再利用できる。
ただし通常の提出の流れでは段階 1 だけで再検査の大半が消えるので、効果を測ってから判断する。

## 検証計画

- 等価性: 提出パターンのコーパス (パーツ追加、本体のみ変更、互換な型変更、依存先を壊す型変更、
  参照先の削除、型パーツの変更、改名) で、旧分類と新分類の受理・拒否とエラーメッセージが
  一致することをテストする。既存のテストスイート (提出まわりの worker テストを含む) が無変更で通ること
- 性能: 測定用の提出ベンチで、`definy` への 1 パーツ追加・本体のみ変更が約 0.4 秒以下に
  なることを目標にする。型パーツの変更では依存先だけが再検査されることを、再検査された
  パーツ数の観測で確かめる
- seed の不動点: core の seed を編集するので、`build:seeds` の再生成と seed の書き出し
  (export) の往復が一致すること、関連する固定点のテストが通ること

## 未決事項

- `sig` のハッシュ計算を definy の中で行うか、エントリのキー (content hash) の組み合わせを
  そのままキーとして使うか (連結した文字列でも衝突耐性は content hash 由来で足りるはず)
- 参照の閉包を辿るときの深さ上限と循環 (型の相互再帰) の扱い: 訪問済みの集合を持ち、
  循環では既出の `sig` を使わない固定値に寄せるなど、決定的になる決め方が要る
- `without_expression` に入るパーツ (型はあるが式が無い) の扱いは現行の分類をそのまま残す想定だが、
  実装時に分類の全分岐を洗い直す
